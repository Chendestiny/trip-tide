## 2026-09-15 —— 分天模型重写 + 一键 AI + 数据层扩充

这一天做了 9 个提交，其中 6 个改变了架构或数据结构。

### 1. 分天模型 v2：地理优先的片区簇（重大）

**旧算法**：最近邻成链 → 按**游览时长**均分切成 N 段。
问题：切点仅由时长决定，把「锦里古街↔武侯祠」这种相距 **0.24km** 的景点切到了两天。

**新算法**：`planner.assign_days()`

```
① 大景点 / 远郊  → 独占一天
② 其余按直线距离聚类成「片区簇」（≤1200m 并簇，single-linkage）
③ 簇分配到天：簇太多就合并最近的两簇；太少只在「真断点」处拆
④ 天与天按地理顺路排序
⑤ 每天内部应用时段硬规则
```

**簇是分天的原子，不可拆** —— 紧邻景点必然同日。

**两个调参教训（都已写进代码注释）**：

| 坑 | 原因 | 解法 |
|---|---|---|
| 聚类阈值用「通行 ≤15 分钟」会把 7 个市区景点连成一整簇 | 速度模型有「1.5km 内一律步行」+「耗时取整到 5 分钟」两个噪音，0.6km 与 1.4km 都算步行、耗时却差 3 倍，阈值在 8~15 分之间出现悬崖 | **改用直线距离 ≤1200m**，实测与行政区划吻合 |
| 分配成本只算游览时长 | 远郊景点游览 1 小时、往返却要 3 小时 | 新增 `_group_load()` = 游览 + 路程；大熊猫基地实测 180 → **260** 分 |

相关函数：`grade_attraction` / `is_remote` / `travel_minutes` / `travel_matrix` /
`cluster_attractions` / `_split_cluster` / `_group_load` / `_alloc_clusters_to_days` /
`estimate_days_needed`

### 2. 弹性游玩时长

景点排得少的日子，余量还给景点本身，而不是塞一个假的「自由活动」节点：

```
最终游玩 = clamp(可用游玩 × r, 基础游玩, 基础游玩 × m)

节奏      填充率 r   倍数上限 m
轻松      0.80      1.00（不扩，早点收工）
平衡      0.95      1.25
紧凑      1.00      1.50（填满）
```

**大景点与远郊不受节奏限制**，一律可扩到 1.5（都江堰玩一整天很正常）。

配套：大景点跨午饭窗口时把午餐插在**景点中途**（上午段 → 午餐 → 下午段，
两段都 ≥30 分钟才拆），否则午饭会被拖到 15:00 之后。

相关函数：`meal_minutes`（新增）/ `_flex_scale` / `_estimate_travel` / `_split_cluster`

### 3. 紧凑度判定重写

**旧指标**：`load`（时间占用率）+ 舍弃率。
问题：`load` 的分子分母**同随天数增长**，加天数几乎不动 —— 算不出「6 天只排了 4 天的量」。

**新指标**：把**勾选景点的总游览时长**摊到每天，与节奏目标比：

```
日均游览 = Σ(勾选景点的 visit_minutes) ÷ 天数
节奏目标 = 轻松 240 / 平衡 360 / 紧凑 450 分钟
ratio ≥ 1.5 → 超载 ｜ ≥ 1.0 → 紧凑 ｜ ≥ 0.65 → 适中 ｜ 否则 轻松
（+ 弃舍兜底：有景点被丢 → 至少「紧凑」；丢弃比例 > 25% → 「超载」）
```

用「勾选总量」而非「排入总量」：后者随天数增加而增加（天数多 → 丢得少），
会让日均**不降反平**。

### 4. 时间预算的硬约束（修超时 BUG）

用户报「最后一天设 16:00 返回，却排到 19:25」。三个原因叠加：

| # | 原因 | 修法 |
|---|---|---|
| 1 | `day_budget` 乘了倾向系数 ×1.15 —— 但出发/返回时间是**用户定的硬约束**，物理时间不会变。420 分钟被算成 483 | 去掉系数；倾向差异只体现在 `PACE_TARGET_MINUTES` 与弹性填充 |
| 2 | 晚餐与回酒店**无条件追加**，且锚点固定 18:00 | 新增 `meal_minutes(end)`：吃完赶不上返回就不排晚餐，直接回住宿片区收尾 |
| 3 | `trim_day` 按「市中心往返」估算，与物化按住宿片区实算差十几分钟 | `materialize_day` 收尾前加最后一道硬约束：仍超时就压缩最后一个景点停留（下限 20 分钟） |

**`strict_return = 最后一天 and 用户显式设了 last_day_return_time`** ——
中间几天回来晚十几分钟照常吃晚饭（只给超时提示），只有赶返程那天才严格卡点。

### 5. 一键 AI：新接口 `/auto-plan`

用户要求「新写一个接口、新按钮，复用现有 AI 规划」。**完全不动 `/plan` 的契约**。

```
POST /api/trip/auto-plan
  → schemas.AutoPlanRequest（城市 + 天数 + 节奏）
  → service.generate_auto_plan()
      ├─ planner.pick_attractions()  自动挑景点（必去优先 → 热度其次，逼近节奏目标）
      └─ 转成普通 PlanRequest → 调**同一个** generate_plan()
```

因为最后走同一条链路，一键与勾选的产出结构、`source` 标记、降级行为完全一致。

前端：`/trip/pick` 顶部加「直接生成 | 详细规划」模式切换。

### 6. 数据层扩充：`best_time` 字段 + `trip_spot` 子表

**动因**：景点内部攻略（入口/时段/门票/小吃）2~3 年不变，不该每次让 LLM 现写。

| 改动 | 说明 |
|---|---|
| `Attraction.best_time` | `morning` / `night` / `museum` / 空。`time_rule()` **优先读它**，原关键词表（含「洪崖洞」「九眼桥」等具体地名）降级为兜底 → **换城市零改动** |
| `trip_spot` 新表 | 景点内部子景点：`name` / `lat` / `lng`（**可为空**）/ `guide` / `order_index` / `stay_minutes`。唯一约束 `(attraction_id, name)` |
| 接口 | `GET /api/trip/attractions/{id}/spots`（单独接口，不塞进 `AttractionOut` —— 列表页用不到，带上响应会翻几倍） |
| seed | 提示词要求每景点给 3~6 个子景点，`guide` 写「怎么玩」；**明确禁止模型写坐标**，改由 `_fill_spot_coords()` 用高德搜「{景点名}{子景点名}」补 |

**轻量迁移**：项目没引 alembic，`core/db.py` 新增 `_ensure_columns()` ——
模型加了列而库里没有就自动 `ALTER TABLE`，幂等零依赖。
**以后给模型加字段，往 `_ADDED_COLUMNS` 加一行即可**（新表不用管，`create_all` 会自动建）。

### 7. LLM 分天审阅（阶段 ①.5）

在「硬编码分天」与「并行写内容」之间插一步：`llm.plan_days_with_llm()`。

**关键是给它量化通行时间矩阵**，不是让它猜距离 —— 这样才不会重演
「凭常识把熊猫基地排到下午」。

输出过 5 道硬校验才采纳（`llm._validate_days`）：id 不重不漏 / 天数相符且无空天 /
**紧邻必须同天** / 独占型独占一天 / 每天不超预算。
两次都不过就**沿用硬编码结果**，所以这一步是纯增益，不引入新的失败面。

### 12. 目的地抽象：region 类型 + 贵州环线 + 链式转场引擎（重大）

**问题**：城市模型装不下「贵州」（贵阳本身没景点，主力在黄果树/万峰林/小七孔，分散全省）和新疆。

**定案**：不建省/市层级，把 `City` 泛化为「目的地」——
`kind=city`（城市+周边，现状 8 城）/ `kind=region`（区域游多基地环线）。
景点 `city_id` 仍单挂一个目的地，**多入口的景点重复在数据层天然不存在**。

- 首页 **2 个 tab（城市 | 区域）** 按 kind 过滤；region 卡片带「环线」角标。
  省份拆分（新疆拆北疆/伊犁/南疆、川西）= 各建一个 region 目的地行，无需新结构
- 子区域多选不加层级：TripPick 景点池顶部 **district 筛选 chips（可多选）**，勾选即组合；
  「全选」只作用于可见集合
- **贵州已落地**（首个 region）：20 景（黄果树 560 / 小七孔 500 / 梵净山 480，高德校准 20/20）
  + 8 个过夜基地（贵阳/安顺/兴义/荔波/凯里/镇远/江口/赤水）

**链式转场引擎（region 专用，city 目的地行为不变）**：
- `plan_hotels` 双策略：city=常住片区+远郊日就近过夜（不变）；
  region=推进式——第一晚住当天景点就近基地，连住优先（≤OVERNIGHT_KM 不动），
  当天景点离昨晚过夜点太远且本地基地明显更优（<60%）才搬
- `materialize_day` / `trim_day` / `_estimate_travel` 拆分**出发地与收尾点**
  （`depart_from` / `depart` 参数）：转场日从昨晚过夜点退房出发，转场车程真实进时间轴与容量预算
  ——修掉「昨晚住安顺、今早却从荔波出发只要 35 分」的硬伤；depart 节点文案区分转场日
- `plan_fallback` / `llm` 流水线 / `adjust_plan` 全部传递 depart_from

**周边标记（UI 与引擎行为对齐）**：`AttractionOut.distance_km`（离目的地中心直线距离）；
前端 ≥30km 标「🚗 周边」、≥45km 标「🚌 远郊·可就近住」——45km 与引擎 `OVERNIGHT_KM` 对齐。

**遗留缺口**：转场日一天只装得下 1 个大景点（车程吃掉大半天，物理事实）；
`estimate_days_needed` 还没把跨基地转场成本算进「需要几天」。

### 14. 新增微信小程序端 `miniprogram/`

小程序端**另起一个目录**，`frontend/` 与 `backend/` 一行不动。

**为什么不是替换成 uni-app**：uni-app 的价值是「一套代码两端」，但 Web 版要保持现状的话，
它只是个给小程序用的第二工程——和原生小程序比没有明显优势，还多一层构建；而且迁移期间
要把 `vue-router` 换 `pages.json`、入口换 `App.vue`、根 `npm run dev` 编排重写，
**Web 版会停摆**，没法边写小程序边对照。等小程序稳定后再评估要不要合并。

**UI 层复用不了**：WXML ≠ HTML（`<div>`→`<view>`、`<span>`→`<text>`），WXSS 选择器受限，
事件从 `@click` 变 `bindtap`。没有任何机制能让原生小程序渲染 `.vue`。

**逻辑层曾经抽过 `shared/` 真源目录**（Web 走 vite alias 零副本、小程序走脚本同步副本
+ `check:shared` 漂移校验），**已拆掉**。原因：那条路要额外维护一个同步脚本和一条校验命令，
对当前体量不划算。现在的规则是 `frontend/` 与 `miniprogram/` **各自完整、各自独立**。

代价是少量**刻意重复**，改的时候两边一起改：

| Web | 小程序 | 重复的内容 |
|---|---|---|
| `frontend/src/trip-theme.js` | `miniprogram/utils/theme.js` | 按天配色、节点图标、交通/节奏标签 |
| `frontend/src/trip-api.js` | `miniprogram/utils/request.js` | 接口路径、超时、错误文案归一化 |
| `frontend/src/trip-store.js` | `miniprogram/utils/store.js` | 历史上限、去重、轻量投影 |

> 存储键 `triptide.history.v1` 两端同名，**仍然不能改**。两端的 storage 是独立命名空间，
> 同名不会冲突也不会互通。

**必须重写的只有一个组件：地图。** `TripMap.vue` 依赖高德 **JS API** + `window._AMapSecurityConfig`，
小程序没有 DOM，根本用不了，要换成 `<map>` 组件。好在全库坐标已是 GCJ-02，腾讯 `<map>` 直接吃（铁律 4），
而且 marker / polyline **不需要 key**。后端继续用高德，腾讯 Key 只用于小程序端。

**待验证假设**：`miniprogram/` 下的 `.js` 全用 ESM 写法（`export` / `import`）。微信官方文档以
CommonJS 为主，但开发者工具支持 ES6 模块并会转译。**首次导入开发者工具时若报模块语法错误**，
说明假设不成立——把小程序侧的 `export`/`import` 改成 `module.exports`/`require` 即可，
只动小程序这一侧（这正是「两个文件夹各写各的」的好处）。

## 2026-09-16 —— 首页排序换算法 + 一批 UI 优化

### 1. 首页宫格排序：改为「前十景点热度累计」

`service.list_cities` 从按 `City.heat` 排序，改成按**每个目的地前 10 高热度景点的 heat 之和**。
新增 `_city_heat_rank()`，一条窗口函数查询
（`ROW_NUMBER() OVER (PARTITION BY city_id ORDER BY heat DESC)` → `WHERE rn <= 10` → `SUM(heat)`），
**不做 N+1**，数据量再涨也只多扫一遍 `trip_attraction`。MySQL 8 / SQLite 3.25+ 都支持。

**排序结果变化很大 —— 成都从第 1 掉到最后**：

| 名次 | 旧序（`City.heat`） | 新序（top10 累计） |
|---|---|---|
| 1 | 成都 | 北京 |
| 2 | 北京 | 上海 |
| 3 | 上海 | 西安 |

### 2. `kind` 的判定标准是「住宿基准」，不是行政区划（重要）

读 `planner.plan_hotels` / `_plan_hotels_region` 得到的**确切**语义：

| kind | 住宿基准 | 行为 |
|---|---|---|
| `city` | **一个常住片区**（`pick_hotel` 取全程景点几何中心最近的片区） | 某天平均离它 >45km（`OVERNIGHT_KM`）且本地有明显更优片区（<60%）→ 建议「就近住一晚」 |
| `region` | **今晚住哪 = 今天走到哪**（推进式） | 第一晚住第一天景点就近基地；离昨晚 ≤45km 就**连住**；否则搬 |

**两者都支持链式转场**（`run_pipeline` 都传 `depart_from=hotels[idx-2]`）。
所以 region 不是「能换酒店」的开关，只是**默认倾向不同**：city 以「不换」为常态、换是例外；region 反过来。

实测距离（高德真实坐标）：

| 目的地 | 市中心 → 主要景区 | 结论 |
|---|---|---|
| 泰安 | 泰山 6.9km、岱庙 4.1km、红门 4.1km | **全在城内**，连「周边」标记都不会有 → `city` |
| 黄山 | 黄山风景区 **50.2km**、宏村 **46.3km**、西递 39.1、屯溪老街 3.3 | 50/46 越过 45km 线，引擎**自动**给「就近住一晚」→ `city` 正好够用 |
| 桂林 | 象鼻山 12.3、遇龙河 57.0、阳朔西街 60.3、兴坪 50.1、龙脊 59.6 | 边界案例，但 city 的 45km 规则同样推出「市区 1 晚 + 阳朔 2 晚 + 龙脊 1 晚」 |

**所以泰山 / 黄山 / 桂林全部按 `city` 录。** 理由：city 与 region 对这三者产出的行程几乎等价，

### 3. 修掉 `deepseek-flash` 的空返回 bug（重要，一次修活三个阶段）

**现象**：`seed --city 深圳` 返回 `DeepSeek 生成名单失败（模型返回内容为空）`，写入 0 个景点。

**根因**：`deepseek-flash` 是**混合思考模型**，默认就会思考，而**思考内容同样计入 `max_tokens`**。

```
max_tokens=4096  →  finish_reason='length'  content=0 字   reasoning=7416 字   ❌
max_tokens=8192  →  finish_reason='stop'    content=8952 字 reasoning=0 字     ✅
```

预算被吃光时返回的是**空 content**，所以 `extract_json` 报的是「模型返回内容为空」——
一个**完全指错方向**的报错，看起来像模型没说话，实际是它把话说在了 `reasoning_content` 里。

**更坑的是原来的写法根本没生效**：

| 参数 | 结果 |
|---|---|
| `extra_body={"enable_thinking": False}`（原代码） | ❌ 照样思考（reasoning 1721 字、content 0 字） |
| 什么都不传 | ❌ 照样思考 |
| `{"chat_template_kwargs": {"enable_thinking": False}}` | ❌ 照样思考 |
| **`{"thinking": {"type": "disabled"}}`** | ✅ 思考已关 |
| `{"reasoning_effort": "none"}` | ✅ 思考已关 |

`enable_thinking` 是 DashScope（通义）风格的参数，**DeepSeek 官方端点不认**，传了等于没传。

**修法**（`core/_llm/_native.py` 的 `_build_body`）：改用 `thinking: {"type": "disabled"}`。

**影响面比 seed 大得多** —— `llm.py` 里三处硬编码的小预算全部受同一根因影响，
只是它们都有 try/except 兜底，所以**一直在静默降级**：

| 阶段 | 原 `max_tokens` | 之前的实际行为 |
|---|---|---|
| ①.5 LLM 审阅分天 | 2000 | 思考一上来就吃光 → `review_days skipped`（静默退回硬编码分天） |
| ② 并行写内容 | 2000 | 该天回退规则文案；全天失败则整份降级 `source=fallback` |
| ④ 终检 | 1200 | `review=null`，方案总述退回兜底文案 |

修完后实测：`source=llm`、三天全部 `gen_day ok`、`review` 有 5 条意见、
`materialize elapsed=5.9~6.7s`（文档里记的 17.7s 是**旧模型/带思考**时的数字）。
单次调用的 completion_tokens 从 1024+ 掉到十几，**思考关掉不影响产出质量**
（对比了厦门「思考开」与三亚/桂林/武汉「思考关」的名单：真实景点、热度分档、`best_time` 标注都正常）。

**附带加固**（`trip/llm.py` 的 `chat_json`）：默认 `max_tokens` 4096 → 8192；
拿到空 content 时**自动加倍重试一次**（上限 16384）。厦门那次就是靠这个重试救回来的
（第 1 次 8192 被思考吃光，第 2 次 16384 成功）—— 保底逻辑值得留着。

景点要分布在这些基地附近」。重灌后西疆拿到 12 个真伊犁景点

### 1. `/api/trip/cities`：70 条 SQL → 1 条，3.4s → 0.09s

> ⚠️ **本节是中间过程**：这里的 `_destination_stats()` 方案后来在**第 4 节**被「排序分预存」取代
> （`rank_score` 预存进 `trip_city`，`/cities` 不再现算）。保留它是因为 N+1 的根因、
> 测量方法和「往返次数下限」的论证过程都在这里。

**实测（改造前）**：返回 68 个目的地，**墙钟 3421ms、70 条 SQL、SQL 累计 2802ms**。

根因是 `list_cities` 里的 `len(c.attractions)` —— relationship 默认懒加载，**68 个目的地就是 68 条 SELECT**，
把 825 行景点全量水合成 ORM 对象。而库在**远端**（自建 MySQL，非本机），实测**单条极简 SELECT 平均往返 38.6ms**，
68 × 38.6ms ≈ 2.6s 就是纯网络排队。

> 为什么以前没暴露：`_city_heat_rank` 本身的注释写着「**不做 N+1**」——那句是对的，
> 但同一个函数的下一个语句 `len(c.attractions)` 就是个 68 连击，注释把人骗过去了。

**改法**：

1. `_city_heat_rank()` → `_destination_stats()`：**一条子查询同时算两个数**
   （`attraction_count` = `COUNT(*)`、`top_heat` = `SUM(CASE WHEN rn<=10 THEN heat END)`），
   再用 `LEFT JOIN` 挂到 `select(City)` 上 → **整条接口只剩 1 条 SQL**。
2. 排序下沉到 SQL：`top_heat DESC, City.heat DESC, City.id ASC`（末位 tie-break 是必需的，
   否则「湘西 / 苏州」这种同键城市两次返回顺序可能不同）。
3. 结果进**进程内缓存**（`settings.cities_cache_ttl`，默认 300s）——目的地只在 seed 时变，
   而前端每次进首页（含从景点页返回）都会调这个接口；`seed` 完成后调 `service.clear_cities_cache()` 立刻失效。

**实测（改造后）**：**1 条 SQL**、**60~160ms**（同一台远端库本身就有波动，多次测量：62 / 91 / 118 / 130 / 162）；
缓存命中 **0ms / 0 条 SQL**。相对 3421ms **提速约 20~55 倍**，SQL 条数 **70 → 1**。
**正确性**：写脚本逐条比对——68 个目的地的**顺序与 `attraction_count` 与旧实现完全一致**（含并列项）。

> 顺带量到：`list_attractions('成都')` = 227ms / 3 条 SQL。也是被远端 RTT 支配（3 × 40ms），
> 但那是景点池页，这次没动。

### 4. 首页排序算法重写：TOP 10→8 + 指数加权 + **排序分预存**

起因：问「热度排序算法合理不合理」，结果发现**旧排序键有一个真实缺陷**。

**旧算法**：`top_heat` = 每个目的地**前 10 高热度景点的 heat 之和**，并列回落 `City.heat`、再回落 `City.id`。
截断到 10 的**本意**是防止景点多的目的地通吃。

**缺陷（实测数据）**：

| 事实 | 数字 |
|---|---|
| 不足 10 景的目的地 | **35 / 68**（对这 35 个，「前10之和」=「全部景点之和」，**截断根本没生效**） |
| 其中恰好 8 景的 | **30 个** —— 是 seed 给名单时的默认规模，**不等于目的地的真实丰富度** |
| 被「数量」压得最狠的 | 泰安 **67 名**（6 景，最高热度 720 = 泰山）；北疆 **53 名**（6 景，均分 390） |
| 被「数量」抬得最狠的 | 深圳 **32 名**（19 景，最高才 420）；湘西 36、呼伦贝尔 33、鲁南 41 |

**结论：旧排序键事实上退化成「景点数量 × 人均热度」，而「景点数量」这一半信号是数据录得全不全，不是值不值得去。**

#### 新算法

```
score = Σ_{i=1..min(8, n)}  heat_i × 0.9^(i-1) × B_i
其中 B₁ = 1.5（城市名片），B₂ = B₃ = 1.2，其余 = 1
```

| 项 | 值 | 依据 |
|---|---|---|

### 7. 修掉 region（环线）排程的两个误判（用户实测发现，两份实现同步修）

**现象**：区域 tab 选河西走廊 → 只勾莫高窟（240min）→ 紧凑 / 1 天：
预估报「**超载** · 排入 1/1 · 会舍弃 1 个（莫高窟）。加到 2 天」；加到 3 天**照样舍弃**，
且文案自相矛盾（「日均游览约 240 分钟，远超 450 分钟目标」—— 240 < 450）。

**根因（三层叠加，后端联机版同样有）**：

| # | 问题 | 位置 |
|---|---|---|
| 1 | `_cost` / `trim_day` 用「目的地**中心**往返」估路程 —— 环线横跨上千公里，中心到莫高窟往返 +10h，单日预算 570×1.5=855 被 874 超过 → 判「装不下」 | `planner._cost` / `_is_standalone` |
| 2 | **预览与真实生成口径不一致**：真生成先按当天景点选住宿片区（region 流程会选到敦煌一带）再裁剪，所以生成排得下；`preview_plan` 裁剪时没传 `origin`，退回市中心 → 预览说超载 | `service.preview_plan` |
| 3 | region 的 `_is_standalone` 也按「市中心单程 ≥45min」判 → **所有景点都是独占型** → 1 天只排 1 个点，另一个直接消失（云南：丽江古城+玉龙雪山选 1 天只排 1 个） | `planner._is_standalone` |

**修法**（`planner.py` + `engine/planner.js`/`rules.js`/`preview.js` + `service.py` 同步）：

1. `_cost` / `_is_standalone`：region 改按**最近的过夜基地**（`hotel_areas`）算往返/单程 ——
   与「当天从哪个基地出发」的生成口径一致；city 不变。
2. `preview_plan` 的逐天裁剪传 `origin = plan_hotels(...)` 的当天住宿片区（镜像 `plan_fallback`）。
3. 文案：有舍弃但日均未超标（ratio < 1）时，改为「本不算多…装不下的原因是路程太远或单点耗时太长」，
   不再喊「远超目标」。
4. 连带修一个被暴露的午餐启发式缺陷：「下来后再吃」若会拖到 15:00 之后则宁可等
   （实测南疆 Day6：10:00 到达、拒绝等 80 分钟、午餐 16:40）；
   以及抵达已过午段（≥15:00）的长途转场日**不再单列午餐**（南疆 Day6 库车→喀什 460min），
   `check_planner` 的午餐口径同步为「0 个须为首景晚于 15:00 到达」。

**回归（全绿）**：
- 用户场景（`local/check-preview-region.mjs`）：莫高窟 1 天/3 天 → 排入 1/1、舍弃 0、判定「轻松」✓；
  云南 2 景 1 天合计 540min → 判「超载」属正确（量真的超标）✓
- 两份引擎对照：12 用例 / 195 节点零差异（区域用例的输出因修复而变化，两侧变化一致）
- `check_planner.py`：29 ✓ / 0 ✗（含新增的转场日午餐口径）
- mock 单文件端到端（无头 Edge，file://）：河西走廊 → 勾莫高窟 → 紧凑 1 天 → 预估不再超载、方案可生成 ✓

**教训**：预览（`preview_plan`）与生成（`plan_fallback`）是两条独立路径，
**裁剪口径必须逐参数对齐**（连 `trim_day` 的 `origin` 都不能差）——
不然就会出现「预览说装不下、生成却排得下」的精神分裂。region 的几何参照点一律用过夜基地，不用中心。
