## 一句话架构

**硬编码分天 → LLM 审阅分天 → LLM 并行写内容 → 硬编码物化时间轴 → LLM 终检。**

```
   阶段 ①  硬编码分天        瞬时、确定、不花钱
            大景点/远郊独占一天 → 其余按直线距离聚成「片区簇」→ 簇分配到天
            地理顺路 + 容量裁剪 + 时段排序（熊猫基地排上午这类硬知识在这里生效）
            ⭐ 片区簇是分天的原子、不可拆 —— 紧邻景点必然同日

   阶段 ①.5 LLM 审阅分天     把**量化通行时间矩阵**给模型提调整建议
            输出过 5 道硬校验才采纳；两次不过就用 ① 的结果（纯增益，无新增失败面）

   阶段 ②  LLM 并行写内容    每天一路，ThreadPoolExecutor 并发
            每路只产出：当天主题 + 各景点建议 + 餐饮区域与本地特色

   阶段 ③  硬编码物化        瞬时、确定
            materialize_day：时间、饭点、路程全部算出来
            含弹性游玩时长填空、跨午饭拆分、目标返回时间的硬约束

   阶段 ④  LLM 终检          读最终时间轴，提意见 + 润色总述
```

分工边界：

```
        LLM 负责                          硬编码负责
        ──────────                        ──────────
   ✅  审阅分天（读矩阵提建议）      →   只采纳通过硬校验的结果
   ✅  起主题名、写具体建议            ❌ 不参与
   ✅  推荐餐饮区域与本地特色          ❌ 不参与
   ✅  复核动线合理性                  ❌ 不参与
   ❌  算时间（到达/停留/路程）    →   ✅  materialize_day()
   ❌  插午晚餐、判断饭点          →   ✅  按 11:20 / 18:00 锚点插入
   ❌  判断装不装得下              →   ✅  prune_to_capacity / trim_day
   ❌  记住哪个景点排过了          →   ✅  工具层强制去重
   ❌  判断景点该上午还是晚上去    →   ✅  time_rule() 优先读 best_time 字段
   ❌  决定住哪个片区              →   ✅  plan_hotels()
   ❌  把紧邻景点分到两天          →   ✅  cluster_attractions() + 分天硬校验
```

## 为什么不让 LLM 自己编排

第一版是让模型用 10 个工具（function calling）自己编排：
`get_city_info → list_attractions → plan_days → build_day ×N → finalize_plan`。
它能跑，而且产出质量不错，但有两个问题。

### 问题一：慢

实测 **26 次工具调用、7~8 轮 API 往返、1.1 分钟**。慢的原因不是模型慢，而是：

1. **轮次天然串行**——每轮都要等模型想完才发下一次，N 天就是 N 次等待；
2. 模型大量时间花在**重新推导硬编码已经算好的东西**（分天、路程、容量）。

改成并行流水线后：**17.7 秒，快 3.7 倍**（4 天 10 个景点）。
2026-09-16 关掉模型思考（`thinking: {"type": "disabled"}`）后进一步降到 **6~7 秒** —— 见 `CHANGELOG.md`。
每天一路互不依赖，N 天只花 1 路的墙钟时间。

### 问题二：模型会把分天改坏

这是更根本的原因。实测它把 **熊猫基地挪到 14:20**（熊猫午后在睡觉）、
把宽窄巷子排进两天、把晚餐合并成 14:05 的「下午茶」。
提示词里写了两遍规则都没拦住——因为「算不算得下」本来就不该由它判断。

现在分天由硬编码负责，模型拿不到改的机会；时段规则更是硬性拒绝
（`build_day` 返回 `ok:false` 并指名怎么改）。

### 代价与保留

模型失去了「探索」能力（不能自己试算某天塞不塞得下）。
但实测它的探索结论基本等同于 `plan_days` 的输出，这部分能力本来就没产生价值。

`tools.py` 那套 10 个工具的 function calling 编排**代码仍保留在仓库里**，但**当前没有任何调用方**
（`run_tools` / `TOOL_SPECS` / `dispatch` / `is_finalized` 全仓库零引用）。`llm.py` 模块注释里
「用 `LLM_MODE=tools` 打开」的开关**从未实现**，`config.py` 里也没有这个字段。
唯一仍在使用的部分是 `tools.audit_day()`（被 `service.audit_plan` 调用做运行时复核）。

> 想让模型重新深度介入分天，需要先补 `LLM_MODE` 开关与对应的调度分支，
> 而不是改一个环境变量就能生效。清理建议见 [`DEVELOPMENT.md`](DEVELOPMENT.md#待办与建议)。

### 那为什么 2026-09-15 又把 LLM 请回来审阅分天？

因为**这次的输入不一样**。

旧方案的模型手里只有「景点名 + 一句话简介」，距离全靠常识猜 —— 于是把熊猫基地
猜到了 14:20。新方案（阶段 ①.5）给的是**预计算的通行时间矩阵**（分钟），
它不需要猜，只要读表判断「哪几个该在一起」。

再加 5 道硬校验兜底，模型**只可能改好、不可能改坏**：

- id 不重不漏 / 天数相符 / 无空天
- **紧邻（≤1.2km）必须同天** ← 把「地理第一」写成硬约束
- 独占型独占一天 / 每天不超预算
- 两次都不过 → 直接沿用硬编码结果

所以这不是「又回到旧方案」，而是**在硬编码打好的骨架上做一次可被拒绝的微调**。

## 交通模型（三档 × 三种偏好，纯本地计算）

用户只选一个大方向，具体方式由硬编码按距离与场景挑。

> **重要：`POST /api/trip/plan` 生成规划时不调用高德路径规划 API。**
> 它只读取已经落库的 GCJ-02 坐标，在本地用 haversine 算直线距离，再按交通方式分档估算通行时间。
> 这样一次规划十几条腿不会产生十几次外部请求，速度稳定，也不会消耗高德路径规划额度。

高德在本项目中的调用边界是：

| 阶段 | 高德接口 | 当前状态 | 说明 |
|---|---|---|---|
| seed 补坐标 | `/v3/geocode/geo` | **已接入，主路径** | 景点名/地址 → GCJ-02 坐标；基础 LBS 配额 15 万/月 |
| seed 坐标兜底 | `/v3/place/text` | **已接入，低频兜底** | 地理编码失败才调用；POI 关键字搜索配额 5 千/月 |
| 前端地图 | 高德 JS API | **已接入，可选** | `VITE_AMAP_JS_KEY` 存在时渲染地图，否则用 SVG 示意图 |
| 生成规划 | 路径规划 API | **未调用** | 只走本地 `planner.leg()` / `haversine_km()` |
| 行程定稿后校准 | `/v3/direction/driving` 等 | **待做** | 用户确认最终方案后，按路段/天缓存真实耗时，再替换估算值 |

**不接高德路径规划 API**，是当前阶段的有意取舍，不是遗漏：一次规划十几条腿，每条都打接口既慢又费配额，
而规划阶段的精度要求不高（约 ±10 分钟不影响方案可用性）。如果未来接入，必须放在「用户确认行程」之后，
不能让它成为生成方案的前置依赖；高德不可用时仍要保留本地估算兜底。

| 场景 | 🚗 自驾 | 🚕 打车+公共（默认） | 🚇 公共交通 |
|---|---|---|---|
| ≤1.5km | 步行 | 步行 | 步行 |
| 城区内 ≤6km | 自驾 30km/h | 打车 26km/h | 地铁公交 22km/h |
| 城区内 6~30km | 自驾 30km/h | 地铁 22km/h | 地铁公交 22km/h |
| 近郊 30~80km | 自驾·高速 62km/h | 顺风车 50km/h | 城际大巴 42km/h |
| 远郊 >80km | 自驾·高速 85km/h | 城际铁路 130km/h | 城际铁路 130km/h |

每种方式都带固定开销（候车/取车/找车位/上下车），时间取整到 5 分钟。

**「近郊」这一档是关键**：都江堰↔青城山 11.9km，两端都在城区外，
地铁不通、打车不划算，真实选择是顺风车（30 分钟）或城际大巴（40 分钟）。
只看距离会误判成「打车 35 分钟」，只看「是否跨城」又会误判成「高铁」。

实测修正效果：

| 路段 | 单一速度模型 | 现在 |
|---|---|---|
| 成都 → 都江堰（56.6km） | 145 分钟 | 顺风车 80 分钟 |
| 都江堰 → 青城山（11.9km） | 35 分钟 | 顺风车 30 分钟 |
| 都江堰日往返总路程 | — | 自驾 190 / 打车+公共 250 / 公共 290 分钟 |

## 餐饮与住宿：只给区域，不给店名

**餐饮**不写具体店名。店铺随时会换，写了反而误导；而且为每家店调一次地图接口
既慢又费配额。现在给的是「区域 + 本地特色小吃」：

```
11:20  [餐饮]  都江堰景区外南桥/西街一带·本地特色午餐
        推荐本地特色：尤兔头、葱葱卷、老腊肉。就近在当天片区解决，
        别为了一顿饭跨区，会打乱下午的动线。
```

**住宿**一次定全程，不每天换。频繁换酒店是自助游最烦的事之一——每天搬行李、重新认路，
性价比极低。`plan_hotels()` 按「全程景点的几何中心」选一个常住片区，
只有某天离它超过 45km（比如成都行程里的都江堰日）才建议就近过夜：

```
Day 1-2  宽窄巷子/人民公园（全程不换酒店，省去搬行李）
         ⚠️ 注意当天景点平均单程 56 km，建议早出发
Day 3    都江堰市区/南桥（当天在都江堰一带，离常住片区 56km，往返太远，建议就近住一晚）
```

## 分天策略（地理优先）

**核心是「片区簇」** —— 按直线距离把相邻景点聚成一组，簇在分天时是原子、**不可拆**。
这样「锦里古街 ↔ 武侯祠」（实测 0.24km）必然落在同一天。

```
① 容量裁剪   算总预算（**逐天时间窗之和** − 当天实际餐时），
             装不下的按「(热度+必去加成) ÷ 耗时」从低到高丢掉，但**必去最后才动**。
② 独占隔离   「游览 ≥4h」或「单程 ≥45min」的景点各自占一整天。
③ 地理聚类   其余景点按最近邻成链（保证顺路），再在「直线 > 1200m」处断开 → 片区簇。
④ 簇分配     簇太多 → 合并地理最近的两簇；太少 → 只在「真断点（>1200m）」处拆；
             全都紧凑时**宁可让某些天空着**，也不把紧邻景点拆开。
⑤ 逐天裁剪   每天按真实预算（含末站回住宿片区的返程）再裁一次，溢出顺延，最后一天溢出进 dropped。
⑥ 时段排序   早场类提到当天第一位，夜景类压到末尾。
```

**为什么聚类阈值用「直线距离」而不是「通行时间」**：速度模型有
「1.5km 内一律步行」和「耗时取整到 5 分钟」两个噪音 —— 0.6km 与 1.4km 都算步行、
耗时却差三倍，用通行时间做阈值会在 8~15 分钟之间出现悬崖。
实测改用 `≤1200m` 后，聚类结果与行政区划几乎完全吻合。

**首末天的时间窗可以不同**：第一天可能中午才到，最后一天要赶飞机。
`day_window(req, day, total)` 按天取时间窗；`meal_minutes(end)` 还会判断当天
来不来得及吃晚饭（赶返程的日子只扣午餐、也不排晚餐）。

## 时间自洽的实现

`materialize_day()` 是全项目**唯一产出时间的地方**，内部用 `push()` 统一推进：

```python
def push(node):
    nodes.append(node)
    cur_time = parse_hhmm(node.time) + node.stay_minutes   # 唯一的推进点
```

插餐饮节点时传 `gap`（从上一站到餐厅的耗时）；不传就按 `目标时刻 - cur_time` 反推。
所以即使为了凑饭点等了 60 分钟，时间轴依然自洽——`prev.time + prev.stay + cur.gap == cur.time` 恒成立。

这条不变量由两处守着：
- `planner.rule_violations()` / `tools.audit_day()`（运行时）
- `scripts/check_planner.py`（回归，15 个用例逐节点校验）

## 紧凑度预估

`POST /preview` 是纯硬编码的，毫秒级返回，让用户在点「开始规划」之前就知道结果。

**判定用「勾选总游览量摊到每天 vs 节奏目标」**：

```
日均游览 = Σ(勾选景点的 visit_minutes) ÷ 天数
节奏目标 = 轻松 240 / 平衡 360 / 紧凑 450 分钟
ratio    = 日均游览 ÷ 节奏目标

ratio ≥ 1.5 → 超载 ｜ ≥ 1.0 → 紧凑 ｜ ≥ 0.65 → 适中 ｜ 否则 轻松
（+ 舍弃兜底：有景点被丢 → 至少「紧凑」；丢弃比例 > 25% → 「超载」）
```

**为什么不用「时间占用率」**：`load = (游览+路程) ÷ (逐天预算之和)` 的分子分母
**同随天数增长**，加天数几乎不动 —— 它算不出「6 天只排了 4 天的量」这种事。

**为什么用「勾选总量」而不是「排入总量」**：排入量会随天数增加而增加
（天数多 → 容量裁剪丢得少 → 排入更多），用它算日均会导致「加天数时日均不降反平」。
用勾选总量，日均随天数**单调下降**，才符合「多加一天就更松」的直觉。

响应里的 `days_needed`（按片区排最舒服要几天）**只作提示，不参与判定** ——
天数不够时 `assign_days` 会合并簇、每天跨片区跑，实际排得下。

## 倾向微调 vs 重新生成

| | `POST /plan/{id}/adjust` | `POST /plan` |
|---|---|---|
| 耗时 | 毫秒级 | 15~30 秒 |
| 花 token | 否 | 是 |
| 文案 | 沿用原来的 | 重新生成 |
| 分天 | 沿用原来的 | 可能变 |

`pace=packed` 时把原方案里被舍弃的景点尽量塞回有余量的天；
`pace=relaxed` 时按缩小后的预算（×0.82）剔除塞不下的，让每天早点收工。
微调会生成**新的一条记录**，原方案保留在历史里。

## 前端：桌面优先的响应式

**默认渲染宽屏网页版，只有宽度 ≤640px 才切成手机 App 形态。** 同一个 DOM，靠媒体查询切换。

| | 宽屏（≥641px） | 手机（≤640px） |
|---|---|---|
| 容器 | 1120px 居中 | 铺满全屏 |
| 导航 | 顶部导航栏 | 底部标签栏 |
| 景点池 | 左列表 + 右侧粘性设置面板 | 单列 + 固定底部浮条 |
| 结果页 | 时间轴 + 右侧粘性「方案说明」 | 单列，说明落到时间轴下方 |
| 地图按钮 | 页头右侧 | 底部浮条 |
| 重新生成弹窗 | 居中卡片 | 底部上滑 sheet |

**为什么桌面优先**：主场景是「在电脑上规划、在手机上看」，且宽屏信息密度要求更高。
移动优先的写法很容易让宽屏变成「拉大的手机」，反过来则只是少写几条覆盖。

绝大多数差异纯 CSS 就够，只有两处需要 JS 知道形态（`use-media.js` 的 `useIsWide()`）：
设置面板是常驻侧栏还是折叠浮条、地图按钮放页头还是浮条。

## 踩过的坑

### 白屏但刷新就好

路由切换后新页面不渲染、`<router-view>` 输出成空注释 `<!---->`，
但**直接打开或硬刷新同一个 URL 完全正常**。

根因是 `<router-view v-slot>` 外面套了 `<transition mode="out-in">`：离场过渡不完成，
Vue 就不挂载新组件。麻烦之处在于——**编译不报错、接口全 200、控制台几乎没有线索**。

所以有了 `scripts/smoke_ui.py`：无头浏览器跑宽屏 + 手机双视口，
走完 4 个页面 + 真实规划，并回归历史上踩过的每个坑。

### `:disabled="busy"` 里 busy 是空字符串

`busy` 用 `''` 表示空闲，而 Vue 对布尔属性的判断是 `!!value || value === ''`
——因为 `disabled=""` 在 HTML 里就是「禁用」。结果按钮永久禁用。
**布尔属性一律用 `!!busy`。**

### 用 `s.index("</template>")` 改 SFC 结构

给 Vue 文件包一层根节点时，用 `index` 找根模板结尾，
但文件里有 `<template #right>` 插槽——第一个 `</template>` 是插槽的，把结构截断了。
**改 SFC 结构要用 `rindex` 或按行解析。**

### 字体字形不可靠

品牌图标原来用 `☈`，渲染成了「K」。**图标一律用内联 SVG**，
不依赖系统字体是否覆盖该码位。

### 用通行时间做聚类阈值，出现「悬崖」

聚类阈值最早写的是「通行 ≤15 分钟算同片区」。结果成都 7 个市区景点被连成**一整簇**。

根因是速度模型的两个噪音叠在一起：「1.5km 内一律步行」+「耗时取整到 5 分钟」，
导致 0.6km 与 1.4km **都算步行、耗时却差三倍** —— 阈值在 8~15 分钟之间是一道悬崖，
松一格就连成一片、紧一格就全断开。

**改用直线距离 `≤1200m`** 后，聚类结果与行政区划几乎完全吻合。

### 时间预算不能乘「倾向系数」

`day_budget` 原来算了 `(时间窗 − 两餐) × PACE_FACTOR`，`packed` 时 ×1.15。

但**出发 / 返回时间是用户定的硬约束** —— 物理时间不会因为「我今天想玩紧凑点」
就多出 15%。420 分钟的时间窗被算成 483 分钟，凭空多给 63 分钟，
于是「最后一天 16:00 返回」被排到了 **19:25（超时 205 分钟）**。

倾向的差异应该体现在「每天目标游玩时长」和弹性填充上，**不是动时间预算**。

### 弹性拉长游玩时长 → 午饭被拖到 16:35

给大景点做弹性填充后（都江堰从 240 分拉到 360 分），午饭跟着被推后 ——
因为原逻辑是「景点完了再吃」，而景点变长了。回归脚本立刻抓到
`Day1 午餐时间离谱 16:35`。

修法：景点跨越午饭窗口（`arrive < 11:20 < arrive + stay`）时，
把午饭插在**景点中途**：上午段 → 午餐 → 下午段，两段都 ≥30 分钟才拆。
时间轴上会出现两个同名节点（第二个带「（下午继续）」），这是有意的。
