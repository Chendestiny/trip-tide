## 一句话架构

**硬编码分天 → LLM 并行写内容 → 硬编码物化时间轴 → LLM 终检。**

```
   阶段 ①  硬编码分天        瞬时、确定、不花钱
            prune_to_capacity → assign_days → plan_hotels
            地理顺路 + 容量裁剪 + 时段排序（熊猫基地排上午这类硬知识在这里生效）

   阶段 ②  LLM 并行写内容    每天一路，ThreadPoolExecutor 并发
            每路只产出：当天主题 + 各景点建议 + 餐饮区域与本地特色

   阶段 ③  硬编码物化        瞬时、确定
            materialize_day：时间、饭点、路程全部算出来

   阶段 ④  LLM 终检          读最终时间轴，提意见 + 润色总述
```

分工边界：

```
        LLM 负责                          硬编码负责
        ──────────                        ──────────
   ✅  起主题名、写具体建议            ❌ 不参与
   ✅  推荐餐饮区域与本地特色          ❌ 不参与
   ✅  复核动线合理性                  ❌ 不参与
   ❌  算时间（到达/停留/路程）    →   ✅  materialize_day()
   ❌  插午晚餐、判断饭点          →   ✅  按 11:20 / 18:00 锚点插入
   ❌  判断装不装得下              →   ✅  prune_to_capacity / trim_day
   ❌  记住哪个景点排过了          →   ✅  工具层强制去重
   ❌  判断景点该上午还是晚上去    →   ✅  time_rule() 硬知识表
   ❌  决定住哪个片区              →   ✅  plan_hotels()
```

## 为什么不让 LLM 自己编排

第一版是让模型用 10 个工具（function calling）自己编排：
`get_city_info → list_attractions → plan_days → build_day ×N → finalize_plan`。
它能跑，而且产出质量不错，但有两个问题。

### 问题一：慢

实测 **26 次工具调用、7~8 轮 API 往返、1.1 分钟**。慢的原因不是模型慢，而是：

1. **轮次天然串行**——每轮都要等模型想完才发下一次，N 天就是 N 次等待；
2. 模型大量时间花在**重新推导硬编码已经算好的东西**（分天、路程、容量）。

改成并行流水线后：**17.7 秒，快 3.7 倍**（4 天 10 个景点）。
每天一路互不依赖，N 天只花 1 路的墙钟时间。

### 问题二：模型会把分天改坏

这是更根本的原因。实测它把 **熊猫基地挪到 14:20**（熊猫午后在睡觉）、
把宽窄巷子排进两天、把晚餐合并成 14:05 的「下午茶」。
提示词里写了两遍规则都没拦住——因为「算不算得下」本来就不该由它判断。

现在分天由硬编码负责，模型拿不到改的机会；时段规则更是硬性拒绝
（`build_day` 返回 `ok:false` 并指名怎么改）。

### 代价与保留

模型失去了「探索」能力（不能自己试算某天塞不塞得下）。
但实测它的探索结论基本等同于 `plan_days` 的输出，这部分能力本来就没产生价值。

`tools.py` 那套 10 个工具的 function calling 编排**代码仍保留在仓库里**，但**当前没有任何调用方**
（`run_tools` / `TOOL_SPECS` / `dispatch` / `is_finalized` 全仓库零引用）。`llm.py` 模块注释里
「用 `LLM_MODE=tools` 打开」的开关**从未实现**，`config.py` 里也没有这个字段。
唯一仍在使用的部分是 `tools.audit_day()`（被 `service.audit_plan` 调用做运行时复核）。

> 想让模型重新深度介入分天，需要先补 `LLM_MODE` 开关与对应的调度分支，
> 而不是改一个环境变量就能生效。清理建议见 [`DEVELOPMENT.md`](DEVELOPMENT.md#待办与建议)。

## 数据流

```
① 城市选择
   TripHome.vue ──GET /cities──▶ service.list_cities ──▶ trip_city 表

② 勾选景点
   TripPick.vue ──GET /attractions?city=成都──▶ service.list_attractions
                ──POST /preview──▶ service.preview_plan（纯硬编码，毫秒级）
                  ↑ 每改一次勾选/天数/倾向就刷新紧凑度提示

③ 生成方案  ← 核心链路
   POST /plan ──▶ service.generate_plan
                    ├─ 硬编码基线   planner.plan_fallback()（兜底 + 退路）
                    ├─ LLM 并行流水线 llm.run_pipeline()
                    ├─ LLM 终检      llm.review_plan()
                    └─ 落库 trip_plan（入参 + 出参 + 终检 + 轨迹）

④ 重新生成
   POST /plan/{id}/adjust ──▶ service.adjust_plan（复用原分天，纯硬编码，毫秒级）
   POST /plan             ──▶ service.generate_plan（全部重做，走 LLM）

⑤ 历史回看
   TripMe.vue ── localStorage（V1）──▶ GET /plan/{id} 兜底
```

## 交通模型（三档 × 三种偏好，纯本地计算）

用户只选一个大方向，具体方式由硬编码按距离与场景挑。
**不接高德路径规划 API**——一次规划十几条腿，每条都打接口既慢又费配额，
而规划阶段的精度要求不高（±10 分钟不影响方案可用性）。

| 场景 | 🚗 自驾 | 🚕 打车+公共（默认） | 🚇 公共交通 |
|---|---|---|---|
| ≤1.5km | 步行 | 步行 | 步行 |
| 城区内 ≤6km | 自驾 30km/h | 打车 26km/h | 地铁公交 22km/h |
| 城区内 6~30km | 自驾 30km/h | 地铁 22km/h | 地铁公交 22km/h |
| 近郊 30~80km | 自驾·高速 62km/h | 顺风车 50km/h | 城际大巴 42km/h |
| 远郊 >80km | 自驾·高速 85km/h | 城际铁路 130km/h | 城际铁路 130km/h |

每种方式都带固定开销（候车/取车/找车位/上下车），时间取整到 5 分钟。

**「近郊」这一档是关键**：都江堰↔青城山 11.9km，两端都在城区外，
地铁不通、打车不划算，真实选择是顺风车（30 分钟）或城际大巴（40 分钟）。
只看距离会误判成「打车 35 分钟」，只看「是否跨城」又会误判成「高铁」。

实测修正效果：

| 路段 | 单一速度模型 | 现在 |
|---|---|---|
| 成都 → 都江堰（56.6km） | 145 分钟 | 顺风车 80 分钟 |
| 都江堰 → 青城山（11.9km） | 35 分钟 | 顺风车 30 分钟 |
| 都江堰日往返总路程 | — | 自驾 190 / 打车+公共 250 / 公共 290 分钟 |

## 餐饮与住宿：只给区域，不给店名

**餐饮**不写具体店名。店铺随时会换，写了反而误导；而且为每家店调一次地图接口
既慢又费配额。现在给的是「区域 + 本地特色小吃」：

```
11:20  [餐饮]  都江堰景区外南桥/西街一带·本地特色午餐
        推荐本地特色：尤兔头、葱葱卷、老腊肉。就近在当天片区解决，
        别为了一顿饭跨区，会打乱下午的动线。
```

**住宿**一次定全程，不每天换。频繁换酒店是自助游最烦的事之一——每天搬行李、重新认路，
性价比极低。`plan_hotels()` 按「全程景点的几何中心」选一个常住片区，
只有某天离它超过 45km（比如成都行程里的都江堰日）才建议就近过夜：

```
Day 1-2  宽窄巷子/人民公园（全程不换酒店，省去搬行李）
         ⚠️ 注意当天景点平均单程 56 km，建议早出发
Day 3    都江堰市区/南桥（当天在都江堰一带，离常住片区 56km，往返太远，建议就近住一晚）
```

## 分天策略（硬编码，五步）

```
① 容量裁剪   先算总预算（天数 × (返回-出发-两餐) × 倾向系数），
             装不下的按「(热度+必去加成) ÷ 耗时」从低到高丢掉。
             先裁再排，避免「排到最后一天才发现塞不下，结果把必去景点丢了」。
② 独占型隔离 「游览 ≥4h」或「单程 ≥45min」的景点各自占一整天。
             不隔离的话最近邻链会把远郊景点排在链尾，和市区景点凑成一天，两头都装不下。
③ 成链均分   剩下的市区景点按最近邻成链，再按游览总时长均分成天。
④ 逐天裁剪   每天按真实预算（含「最后一站回住宿片区」的返程）再裁一次，
             溢出的顺延到下一天，最后一天溢出则进 dropped。
⑤ 时段排序   早场类（熊猫基地）提到当天第一位，夜景类（洪崖洞）压到末尾。
```

**首末天的时间窗可以不同**：第一天可能中午才到，最后一天要赶飞机。
`day_window(req, day, total)` 按天取时间窗，容量按「最紧的一天」保守估计。

## 时间自洽的实现

`materialize_day()` 是全项目**唯一产出时间的地方**，内部用 `push()` 统一推进：

```python
def push(node):
    nodes.append(node)
    cur_time = parse_hhmm(node.time) + node.stay_minutes   # 唯一的推进点
```

插餐饮节点时传 `gap`（从上一站到餐厅的耗时）；不传就按 `目标时刻 - cur_time` 反推。
所以即使为了凑饭点等了 60 分钟，时间轴依然自洽——`prev.time + prev.stay + cur.gap == cur.time` 恒成立。

这条不变量由两处守着：
- `planner.rule_violations()` / `tools.audit_day()`（运行时）
- `scripts/check_planner.py`（回归，8 个用例逐节点校验）

## 紧凑度预估

`POST /preview` 是纯硬编码的，毫秒级返回，让用户在点「开始规划」之前就知道结果。

判定同时看**负载率**和**舍弃比例**——只看负载率会误判：
10 个景点塞进 4 个丢掉 6 个，负载率照样好看，但那显然不是「刚好」。

| tightness | 条件 |
|---|---|
| `超载` | 舍弃比例 > 25%，或负载率 > 1.05 |
| `紧凑` | 舍弃比例 > 8%，或负载率 > 0.88 |
| `适中` | 负载率 > 0.6 |
| `轻松` | 其余 |

## 倾向微调 vs 重新生成

| | `POST /plan/{id}/adjust` | `POST /plan` |
|---|---|---|
| 耗时 | 毫秒级 | 15~30 秒 |
| 花 token | 否 | 是 |
| 文案 | 沿用原来的 | 重新生成 |
| 分天 | 沿用原来的 | 可能变 |

`pace=packed` 时把原方案里被舍弃的景点尽量塞回有余量的天；
`pace=relaxed` 时按缩小后的预算（×0.82）剔除塞不下的，让每天早点收工。
微调会生成**新的一条记录**，原方案保留在历史里。

## 前端：桌面优先的响应式

**默认渲染宽屏网页版，只有宽度 ≤640px 才切成手机 App 形态。** 同一个 DOM，靠媒体查询切换。

| | 宽屏（≥641px） | 手机（≤640px） |
|---|---|---|
| 容器 | 1120px 居中 | 铺满全屏 |
| 导航 | 顶部导航栏 | 底部标签栏 |
| 景点池 | 左列表 + 右侧粘性设置面板 | 单列 + 固定底部浮条 |
| 结果页 | 时间轴 + 右侧粘性「方案说明」 | 单列，说明落到时间轴下方 |
| 地图按钮 | 页头右侧 | 底部浮条 |
| 重新生成弹窗 | 居中卡片 | 底部上滑 sheet |

**为什么桌面优先**：主场景是「在电脑上规划、在手机上看」，且宽屏信息密度要求更高。
移动优先的写法很容易让宽屏变成「拉大的手机」，反过来则只是少写几条覆盖。

绝大多数差异纯 CSS 就够，只有两处需要 JS 知道形态（`use-media.js` 的 `useIsWide()`）：
设置面板是常驻侧栏还是折叠浮条、地图按钮放页头还是浮条。

## 踩过的坑

### 白屏但刷新就好

路由切换后新页面不渲染、`<router-view>` 输出成空注释 `<!---->`，
但**直接打开或硬刷新同一个 URL 完全正常**。

根因是 `<router-view v-slot>` 外面套了 `<transition mode="out-in">`：离场过渡不完成，
Vue 就不挂载新组件。麻烦之处在于——**编译不报错、接口全 200、控制台几乎没有线索**。

所以有了 `scripts/smoke_ui.py`：无头浏览器跑宽屏 + 手机双视口，
走完 4 个页面 + 真实规划，并回归历史上踩过的每个坑。

### `:disabled="busy"` 里 busy 是空字符串

`busy` 用 `''` 表示空闲，而 Vue 对布尔属性的判断是 `!!value || value === ''`
——因为 `disabled=""` 在 HTML 里就是「禁用」。结果按钮永久禁用。
**布尔属性一律用 `!!busy`。**

### 用 `s.index("</template>")` 改 SFC 结构

给 Vue 文件包一层根节点时，用 `index` 找根模板结尾，
但文件里有 `<template #right>` 插槽——第一个 `</template>` 是插槽的，把结构截断了。
**改 SFC 结构要用 `rindex` 或按行解析。**

### 字体字形不可靠

品牌图标原来用 `☈`，渲染成了「K」。**图标一律用内联 SVG**，
不依赖系统字体是否覆盖该码位。

## 已知取舍（V1）

| 项 | 现状 | 要做准需要 |
|---|---|---|
| 通行时间 | 分档经验系数 | 接高德路径规划 API，按天缓存 |
| 餐饮 | 区域 + 本地特色小吃 | 预生成餐饮库并定期刷新 |
| 时段硬知识 | 3 类关键词规则 | 给景点加 `best_time` 字段，seed 时由 LLM 标注 |
| 历史记录 | localStorage，换设备就没了 | 接登录，切到 `GET /plans` |
| 地图 | 缺 JS Key 时是 SVG 示意图 | 填 `VITE_AMAP_JS_KEY` 自动切高德 JS API |
| 账号体系 | 无 | V1 明确不做；迁小程序时接 `openid` |
| 并发 | 单进程，一天一路并行（`MAX_WORKERS=4`） | 改异步队列 + 轮询/SSE |
| 景点上限 | 40 个，超了路由层拦掉 | 分批规划再合并 |
